# Motion Controller — Execution Plan

**Status:** refined for execution. This supersedes the first draft; the substantive
corrections are listed in §0. The plan follows the repo's existing arrangement: the Lean
development under `lean/` is the specification, the Rust under `crates/` is the
implementation, and `test_data/` holds exact ground truth generated by Lean.

**Primary deliverable:** a verified 1-DOF jerk-limited S-curve planner, rest-to-rest first
and general boundary conditions second. The 6-DOF joint-space controller and the Rust
implementation are designed at the same time so the 1-DOF interface does not have to be
changed later.

**At a glance.** M1's guaranteed deliverable is a conservative rational S-curve template,
fully proved in Lean and implemented generically in Rust; the 7-phase optimal planner is
M1-opt, implemented in Rust and tested against exact golden vectors, with Lean proofs
staged (Case A rational, the triangular-cruise/B/C cases radical). M2 is a stop–move–start
planner for arbitrary
boundary states with an exact viability predicate. M3 offers MoveJ-scalar (joint-space
line) and MoveJ-sync (per-joint profiles, common duration). M4 is a headless
tracker/supervisor harness. M5 is a feasibility-first Cartesian certifier, not TOPP. The
Rust polynomial layer is `Field`-generic so exact `Ratio` tests run the same code as
production; the optimal planner is `f64` with `sqrt`/`cbrt`.

## 0. What changed from the first draft

The first draft's architecture is right: an open-loop feasible profile, a tracker, and a
supervisor that only stretches time or re-plans. Several of its mathematical and
formalisation details are not executable as written. These are the corrections.

| Draft | Refined | Why |
| --- | --- | --- |
| `Phase` is an arbitrary `C²` function with an almost-everywhere constant third derivative; its bound field mentions an unbound `jmax` | A phase is a cubic segment determined by its entry state, a constant jerk and a duration | Derivatives become exact polynomials; the a.e. predicate leaves the core definition; the field-scoping bug disappears |
| `d_acc = A(t_j+t_a)²/2 − A t_j²/2 + 2Jt_j³/6` | `d(v) = v(t_j + v/A)/2` when `A` is reached | The draft formula is algebraically wrong: with `A=J=1, t_a=0` it gives `1/3` where direct integration gives `1` |
| Triangular `d = 5/12 · Δv · t_ramp` | `d = J t_r³ = Δv · t_r` | Direct integration of the triangular velocity profile; `5/12` is not the coefficient |
| `v_peak = (6/5 · Δq)^{2/4} · J^{1/2}` | `t_r = cbrt(D/(2J))`, `v_p = J t_r²` | The draft expression is garbled and dimensionally wrong |
| Cases keyed only on `Δq` versus `v_max` | Cases keyed on `D_full(V) = 2d(V)` and `v_A = A²/J` | Reaching `a_max` and cruising at `v_max` are independent regimes; both have to be classified before the durations are computed |
| General boundary conditions: "linearise `a0`, `a1` to zero" | Stop–move–start decomposition with an exact viability predicate for that decomposition | Makes the general planner total inside `Viable`, provable, and honest about impossible stop/start states; it is not a global infeasibility certificate |
| `Feasible` is stated with `∀ᵐ` third derivatives | `Feasible` is velocity/acceleration bounds plus a per-segment jerk bound; a separate lemma links segment jerk to the a.e. third derivative | Simpler to prove and stronger at the representation level; the a.e. statement remains available as a theorem |
| `stretch k` scales durations and jerks only | `stretch k` also scales the start velocity by `1/k` and the start acceleration by `1/k²` | Otherwise the result is not the trajectory `q(t/k)`; the draft version changes the initial state |
| Sync by stretching every joint profile | Sync only for **rest-to-rest** profiles; multi-joint re-planning from a moving state uses a synchronised stop, then a MoveJ | Stretching a profile with nonzero start velocity changes that velocity, so the joints would no longer share the measured state |
| T9: any non-decreasing `s` with `s' ≤ 1` preserves feasibility | Affine reparameterisation is the M4 primitive; `comp_bounds` states the general bounded-rate condition (`S1,S2,S3`), and the supervisor changes rate only at cycle boundaries | `q'' = p''(s)(s')² + p'(s)s''`: a nonzero `s''` can violate the acceleration bound. The draft claim is false as stated |
| T8 mentions `lim.pos` and `vmax + e_max/T_cycle` | Replace with a no-overshoot theorem for rest-to-rest profiles; optional supervisor checks for caller-supplied position limits; no tracking-error theorem in M1–M4 | `Limits` has no position field, and the velocity claim needs a plant/error model that does not exist yet |
| Draft gluing lemma matches derivatives for `k < n` | `contDiff_piecewise_le` matches through order `n` (`k ≤ n`) for globally smooth pieces | The draft is off by one and false: `C^n` gluing needs the n-th derivative to match, and one-sided `iteratedDeriv` at an endpoint is a junk value |
| `stateAt` returns a constant after the last segment | `evalFrom` extends the last cubic; Rust clamps at the end | A constant stub is not `C²` at `T` when the profile ends with nonzero velocity; the extension makes the gluing lemma global |
| Optimal 7-phase planner treated as a straightforward Lean milestone | M1-default (rational template) is the guaranteed verified baseline; M1-opt is the 7-phase planner, Rust + golden-tested, with Lean Case A first and Cases B/C as the radical extension | `sqrt`/`cbrt` case proofs are the schedule risk (4–8 weeks by the formalisation audit); Mathlib has no `Real.cbrt`; the conservative template proves the structural layer without radicals |
| "PID / computed-torque tracker" | Position/velocity feedback tracker; torque and arm dynamics explicitly out of scope | The repo has payload/sensor dynamics only: no mass matrix, no joint torque model, no masses in `robot_parameters.json` |
| TOPP with a `‖J‖` bound | A conservative feasibility-first Cartesian mode, conditional on bounds for `q'(s)`, `q''(s)`, `q'''(s)`; true TOPP deferred | Bounding the Jacobian alone does not bound the induced joint derivatives; TOPP is new theory and a new Jacobian layer |
| Golden harness as a standalone milestone after both implementations | Golden vectors are built incrementally with every planner milestone; the harness is part of each milestone's definition of done | Waiting until both implementations exist makes discrepancies expensive to localise |

## 1. Scope, decisions, non-goals

### 1.1 Deliverables

1. **M1 — 1-DOF rest-to-rest S-curve.** M1-default: a conservative rational template,
   fully proved in Lean, generic over `Field` in Rust, and exact over `Ratio`. M1-opt: the
   7-phase optimal closed form, implemented in Rust and golden-tested, with Lean Case A
   (A reached) first and the triangular-cruise, B and C cases as the non-gating radical
   extension.
2. **M2 — general boundary conditions.** A stop–move–start planner for arbitrary
   `(q, v, a)` at both ends, with a proved viability condition for that decomposition
   (not a global infeasibility certificate) and a matching rejection predicate.
3. **M3 — joint-space MoveJ.** Two explicitly named semantics:
   - **MoveJ-scalar (recommended primary):** fix the joint-space line
     `q(s) = q0 + s (q1 − q0)`, derive effective limits
     `Vs = min_i v_i/|Δq_i|`, `As = min_i a_i/|Δq_i|`, `Js = min_i j_i/|Δq_i|` over the
     joints with `Δq_i ≠ 0`, and plan one S-curve `s(t)`. The joint-space path is a
     straight line by construction.
   - **MoveJ-sync (independent joint timing):** plan one rest-to-rest S-curve per joint,
     then stretch each to a common duration. The induced joint-space path is *not* a
     straight line unless all six profiles happen to be proportional; no path-shape claim
     is made.
   Both modes reduce to the 1-DOF planner; the scalar mode is less proof work and is the
   default unless per-joint profile shapes are specifically wanted.
4. **M4 — tracker and supervisor (Rust).** Time scaling by affine rate changes,
   re-planning from the measured state (using M2), stall detection, and a headless plant
   harness that exercises all of them.
5. **M5 (optional) — Cartesian path mode.** A conservative, feasibility-first
   parameterisation of a smooth path, conditional on smooth-branch and derivative-bound
   assumptions. Not time-optimal TOPP.
6. **Documentation.** `docs/mathematics.md` gains a *Motion control* derivation;
   `docs/lean-rust-map.md` gains the theorem map; `docs/verification.md` gains the
   floating-point boundary; `README.md` names the new crate and commands.

### 1.2 Resolved open questions from the first draft

| # | Question | Decision |
| --- | --- | --- |
| 1 | Lean `ℝ` vs Rust `f64`; which is the reference? | Lean is the specification and the exact-vector oracle. Rust is a hand-written implementation. The conservative M1-default planner is radical-free and generic over `Field`, so it is exact over `Ratio`; the optimal M1-opt planner evaluates `sqrt`/`cbrt` and is compared with a declared tolerance. There is no FFI and no extraction. |
| 2 | General boundary conditions in the first version? | Rest-to-rest is M1. M2 adds a stop–move–start decomposition that reuses M1 and handles arbitrary `(v, a)` endpoints. M4 (re-plan) depends on M2, so M2 comes before the supervisor. |
| 3 | Torque/dynamics in scope? | No. The repository has no arm dynamics or torque model. Tracker output is a velocity/position command; the plant abstraction defines what is commanded. A torque layer is a separate project with new mathematics. |
| 4 | Joint limits: planner or supervisor? | The planner is a point-to-point planner over the reals and does not carry global joint limits, consistent with `docs/verification.md`. A caller-supplied position-limit check belongs in the supervisor. For rest-to-rest moves the no-overshoot theorem reduces the check to the endpoints. |
| 5 | IK branch selection (M5)? | One smooth branch per move, fixed before planning. The Rust controller samples the path for branch changes and singularities and aborts rather than emitting NaN. The Lean refinement theorem assumes a single `C³` branch. |
| 6 | What does MoveJ mean? | Two explicitly named modes. MoveJ-scalar fixes the joint-space line and times it with one S-curve; it is the default because it has a stronger path guarantee and less proof work. MoveJ-sync plans a profile per joint and stretches to a common duration; it preserves per-joint profile shapes but makes no joint-space-line claim. |

### 1.3 Non-goals

- Arm dynamics, torque limits, computed-torque control, or payload effects on the motion
  profile.
- Collision avoidance and obstacle-aware planning. An obstacle is an input to the
  supervisor (a halt/re-plan event), not a planner feature.
- Time-optimal path parameterisation (TOPP) and Cartesian path following in M1–M4.
- Floating-point error bounds, extraction of Rust into Lean, or Lean→Rust FFI.
- High-precision re-runs of the motion property suite. The `Scalar` seal documented in
  `docs/verification.md` still blocks that; the planner is `f64`-only. The polynomial
  layer is `Field`-generic so exact `Ratio` tests can run, but there is no plan for a
  high-precision planner instantiation.
- A GUI for motion in the first pass. M4 is a headless harness; app integration is an
  optional follow-up (§5.6).

## 2. Architecture

```
┌────────────────────────────────────────────────────────────┐
│ Planner (on trigger, offline)                              │
│   input:  start state, target state, limits                │
│   output: Profile = ordered cubic segments (constant jerk) │
├────────────────────────────────────────────────────────────┤
│ Reference clock (per control cycle, Rust)                  │
│   q_ref(t) = profile.eval(s)                               │
│   s advances at rate r ∈ [0, 1]; r changes at cycle bounds │
├────────────────────────────────────────────────────────────┤
│ Tracker (per control cycle)                                │
│   a_cmd = a_ref + Kp e + Kd (v_ref − v_measured), clamped  │
├────────────────────────────────────────────────────────────┤
│ Supervisor (per control cycle)                             │
│   - slow the reference when |e| grows                      │
│   - detect stall: growing error + command saturation       │
│   - re-plan from the measured state on persistent error    │
└────────────────────────────────────────────────────────────┘
```

**Key invariant.** Every `Profile` the planner returns is feasible: its velocity and
acceleration stay inside `v_max`/`a_max`, and every segment's jerk is inside `j_max`. The
tracker and supervisor never modify a profile's geometry. The only runtime operation on a
profile is an **affine time reparameterisation** (a constant rate over an interval), which
preserves feasibility by the stretch lemma. A rate change at a cycle boundary may step the
reference velocity; that is a command discontinuity the tracker absorbs, not a violation of
the profile's feasibility. The supervisor never claims that the concatenated reference is
`C²`.

**Re-planning.** A re-plan replaces the profile with `plan_general(measured, target)`.
For a six-joint move from a moving state, individual re-plans would not share a time base;
the supervisor therefore uses a synchronised controlled stop followed by a MoveJ, or
accepts per-joint arrival times. This is stated as a supervisor policy, not hidden in the
planner.

## 3. 1-DOF mathematics

### 3.1 Representation

```rust
struct Limits<S = f64> { vmax: S, amax: S, jmax: S }   // finite and > 0
struct State<S = f64>  { q: S, v: S, a: S }
struct Segment<S = f64> { dur: S, jerk: S }            // dur ≥ 0, |jerk| ≤ jmax
struct Profile<S = f64> {
    start: State<S>,
    end: State<S>,
    segments: [Segment<S>; MAX_PHASES],
    starts: [State<S>; MAX_PHASES],                    // entry state of each segment
    len: usize,
    total_time: S,
}
```

The position on a segment of local time `τ` is

```
q(τ) = q0 + v0 τ + a0 τ²/2 + j τ³/6
v(τ) = v0 + a0 τ + j τ²/2
a(τ) = a0 + j τ
```

This is the only phase representation used by the planner, the evaluator, the Lean
specification and the golden generator. A `Profile` folds these cubics: each segment starts
at the previous segment's exit state, which is stored in `starts` so phase-boundary values
are exact and available to golden tests. Position, velocity and acceleration are continuous
across a boundary by construction; jerk may jump, which is exactly why the specification is
`C²` and why the jerk bound is stated per segment.

`MAX_PHASES` is 15: seven for rest-to-rest and fifteen for the general stop–move–start
planner (§3.5). Zero-duration phases are **kept**: the Lean list, the Rust list and the
golden list are then structurally identical, and the evaluator skips them. The phase counts
in §3.3 are maxima.

The polynomial layer (`State`, `Limits`, `Segment`, `Profile`, evaluation, `stretch`,
`sync`) is generic over `robot_kinematics::Field`, so the exact rational type in
`robot-golden` runs the same code as production. Only the planner needs `sqrt`/`cbrt`; it
is plain `f64` (§5.1).

### 3.2 Per-half displacement `d(v)`

Let `A = a_max`, `V = v_max`, `J = j_max`, `t_j = A/J`, `v_A = A²/J`.

`v_A` is the smallest peak velocity for which a full acceleration ramp reaches `A`:
with zero constant-acceleration time, a complete ramp-up/hold/ramp-down gains
`A·t_j = A²/J`.

For a symmetric acceleration half from rest to peak velocity `v` (`0 ≤ v ≤ V`):

```
t_r = sqrt(v/J)                              if v ≤ v_A   (triangular)
t_a = v/A − t_j                              if v ≥ v_A   (A reached)
d(v) = v · t_r                               if v ≤ v_A
     = v · (t_j + v/A) / 2                   if v ≥ v_A
```

At `v = v_A` both give `A³/J²`. The formula follows by integrating the cubic; the draft's
"correction term" was an algebraic slip. `d` is continuous, positive and strictly
increasing on `(0, V]`.

The displacement needed to reach peak velocity `V` and immediately decelerate is

```
D_full(V) = 2 · d(V).
```

### 3.3 Rest-to-rest case analysis

Let `Δ = q1 − q0`, `D = |Δ|`, and mirror the positive-displacement solution when `Δ < 0`.
Every rest-to-rest case emits the **same 7-slot canonical list**; a slot the case does not
use has duration zero:

| # | jerk | duration | role |
|---|---|---|---|
| 1 | `+J` | `t₁` | accel ramp-up |
| 2 | `0`  | `t₂` | constant accel |
| 3 | `−J` | `t₃` | accel ramp-down |
| 4 | `0`  | `t₄` | cruise |
| 5 | `−J` | `t₅` | decel ramp-down |
| 6 | `0`  | `t₆` | constant decel |
| 7 | `+J` | `t₇` | decel ramp-up |

For `D > 0`, exactly one of these cases applies:

**Case A — cruise at `V`.** `D ≥ D_full(V)`.

- If `V ≥ v_A` (A reached): `t_a = V/A − t_j`, cruise
  `t_c = (D − D_full(V))/V`, and
  `(t₁,...,t₇) = (t_j, t_a, t_j, t_c, t_j, t_a, t_j)`.
- If `V < v_A` (triangular, still with cruise): `t_r = sqrt(V/J)`,
  `t_c = (D − 2V t_r)/V`, and
  `(t₁,...,t₇) = (t_r, 0, t_r, t_c, t_r, 0, t_r)`.

**Case B — no cruise, A reached.** `D < D_full(V)`, `V ≥ v_A`, and
`D ≥ 2A³/J²` (equivalently `v_p ≥ v_A`). Let

```
v_p = (A/2) · (sqrt(t_j² + 4D/A) − t_j),      t_a = v_p/A − t_j.
```

`v_p` is the positive root of `v_p²/A + v_p t_j = D`, i.e. `2d(v_p) = D`.
`(t₁,...,t₇) = (t_j, t_a, t_j, 0, t_j, t_a, t_j)`.
The two adjacent `−J` phases (slots 3 and 5) are kept separate by the zero-duration
cruise slot; each phase then has a velocity profile with a single sign of acceleration,
which is what makes the feasibility proof local.

**Case C — triangular, no cruise.** `D < D_full(V)` and `D < 2A³/J²`.

```
t_r = cbrt(D/(2J)),      v_p = J t_r².
```

`(t₁,...,t₇) = (t_r, 0, t_r, 0, t_r, 0, t_r)`.

**Case D — zero displacement.** `D = 0`: the empty profile at `q0`, total time zero.

The implementation names these `PlanKind::Cruise` (A), `PlanKind::PeakNoCruise` (B),
`PlanKind::Triangular` (C) and `PlanKind::ZeroMotion` (D). The golden `kind` field uses
the same names.

The 7-slot convention makes the Lean, Rust and golden phase lists structurally identical:
the phase count is always 7 for `D > 0` (plus the empty Case D), and a case that does not
use a slot emits it with duration zero. The evaluator skips a zero-duration phase because
its cumulative end is not strictly greater than the evaluation time (§3.6). Non-threshold
golden cases compare the full segment list; threshold cases compare the trajectory,
because an f64 comparison can legitimately choose the adjacent case at an exact boundary
(§6.4).

**Boundary continuity of the case split.**
At `D = D_full(V)` the cruise duration is zero; Case A and the no-cruise formula produce
the same trajectory. At `D = 2A³/J²`, Case B and Case C both produce
`t_a = 0`, `t_r = A/J`. At `D = 0`, all durations tend to zero. The planner is therefore
continuous across its case boundaries, which matters for the f64 implementation and for
threshold tests.

### 3.4 Rest-to-rest algorithm (M1-opt)

The following is the 7-phase optimal algorithm (M1-opt). The verified default is the
conservative rational template of §3.8, which shares the same 7-slot shape.

```
plan_rest_to_rest(q0, q1, lim):
  Δ = q1 − q0
  if Δ == 0: return empty(q0)
  D = |Δ|
  p = plan_positive(D, lim)          # starts at q=0, ends at q=D, rest at both ends
  p = translate(p, q0)
  return Δ > 0 ? p : mirror(p)

plan_positive(D, lim):
  t_j = A/J; v_A = A²/J; dV = d(V)
  if D ≥ 2*dV:
      if V ≥ v_A:
          t_a = V/A − t_j
          t_c = (D − 2*dV)/V
          return 7-slot profile (t_j, t_a, t_j, t_c, t_j, t_a, t_j)
      else:
          t_r = sqrt(V/J)
          t_c = (D − 2*V*t_r)/V
          return 7-slot profile (t_r, 0, t_r, t_c, t_r, 0, t_r)
  else if V ≥ v_A and D ≥ 2*A^3/J^2:
      v_p = (A/2)*(sqrt(t_j^2 + 4*D/A) − t_j)
      t_a = v_p/A − t_j
      return 7-slot profile (t_j, t_a, t_j, 0, t_j, t_a, t_j)
  else:
      t_r = cbrt(D/(2*J))
      return 7-slot profile (t_r, 0, t_r, 0, t_r, 0, t_r)
```

The jerk signs are fixed by the slot: `(+J, 0, −J, 0, −J, 0, +J)`. A zero duration means
the slot contributes no motion; the state at its start equals the state at its end.
`mirror` negates the start velocity and acceleration and every segment's jerk; it leaves
`q` and the durations unchanged. `translate` shifts the start position. Both preserve
feasibility because the limits are symmetric.

### 3.5 General boundary conditions (M2)

The general planner is deliberately a **stop–move–start** decomposition. It is not
time-optimal, but it is total, provable, and reuses the rest-to-rest planner.

Define `rev(s) = { q := s.q, v := −s.v, a := s.a }`.

**Stop feasibility.** A state can be brought to rest without violating the velocity or
acceleration limits precisely when

```
v_s(s) = s.v + s.a·|s.a|/(2J)

stop_feasible(s, lim) :=
  |s.a| ≤ A  ∧  |s.v| ≤ V  ∧  |v_s(s)| ≤ V.
```

The third term is unavoidable: to bring nonzero acceleration to zero, the fastest legal
jerk ramp takes `|a|/J` and changes velocity by `a·|a|/(2J)`. While `a` has one sign, the
velocity is monotone, so the maximum speed during the ramp is the larger endpoint. If the
result leaves the band, no profile can satisfy the limits: any legal profile must spend at
least that long reducing `a` to zero, and does not gain less speed doing so.

For the target, time reversal gives the matching condition:
`v_e = s1.v − s1.a·|s1.a|/(2J)` must satisfy `|v_e| ≤ V`, which is exactly
`stop_feasible(rev s1, lim)`. Define

```
Viable(s0, s1, lim) :=
  stop_feasible(s0, lim) ∧ stop_feasible(rev s1, lim)
```

which expands to `|v0|≤V`, `|a0|≤A`, `|v1|≤V`, `|a1|≤A`, `|v_s|≤V`, `|v_e|≤V`.
This is the exact **viability** condition for the stop–move–start decomposition: outside
it the stop/start phases cannot stay inside the velocity band, and inside it the
construction below produces a feasible profile. It is not a global infeasibility
characterization — a direct profile that never passes through rest can exist outside
`Viable` (a profile ending with nonzero acceleration is the simplest example). Position
limits and no-overshoot are separate caller constraints, not part of `Viable`.

**Stop profile.** If `a ≠ 0`, emit one ramp segment `(dur = |a|/J, jerk = −sign(a)·J)`,
which brings `a` to zero and velocity to `v1 = v + a·|a|/(2J)`. Then brake from `(v1, 0)`
to rest:

- `v1 > 0`, `v1 ≥ v_A`: `(−J,t_j), (0,t_a), (+J,t_j)` with `t_a = v1/A − t_j`.
- `v1 > 0`, `v1 < v_A`: `(−J,t_r), (+J,t_r)` with `t_r = sqrt(v1/J)`.
- `v1 < 0`: the mirror of the two cases above.
- `v1 = 0`: no brake segments.

**Start profile.** The time reverse of a stop profile:
`start_profile(s1, lim) = reverse(stop_profile(rev(s1), lim))`. It starts at rest at the
position where the reversed stop ends, and ends exactly at `s1`. The implementation may
either define `reverse` or emit the mirrored phases directly; either way the same segment
safety lemma is used.

**General planner.**

```
plan_general(s0, s1, lim):
  if not Viable(s0, s1, lim): return None      # equivalently the two stop_feasible checks
  stop  = stop_profile(s0, lim)
  start = start_profile(s1, lim)
  mid   = plan_rest_conservative(stop.end.q, start.start.q, lim)
  return append(append(stop, mid), start)
```

The three pieces join at rest states, so position, velocity and acceleration are
continuous at both junctions. Each piece is feasible, so the concatenation is feasible by
`feasible_append`. The stopping ramp and the start ramp each contribute at most four
segments (one acceleration-removal ramp plus at most three brake/acceleration phases), and
the middle contributes at most seven: **15 is the exact segment bound**, stated as
`planGeneral_length_le`.

The rejection predicate is exact **for the stop–move–start decomposition**: `None` is
returned iff `Viable` fails, and the middle rest-to-rest problem is always solvable for
finite positions. It is not a global infeasibility certificate. A direct profile that
never passes through rest can exist outside `Viable` — for example, a single segment
ending with nonzero acceleration can stay inside the velocity band even when a
stop-and-restart cannot. The planner deliberately rejects such inputs rather than
searching for a direct profile; `stopFeasible_necessary` applies only to profiles that
actually end at rest.

### 3.6 Evaluation convention

- `eval(t)` clamps `t` to `[0, total_time]` in Rust: `t ≤ 0` returns the start state,
  `t ≥ total_time` returns the end state.
- Otherwise it selects the first segment whose cumulative end is **strictly greater** than
  `t`. At an internal boundary this is the **later** segment. Zero-duration segments are
  skipped automatically because their cumulative end equals their start. Continuity makes
  the choice invisible in exact arithmetic; the convention is pinned so golden vectors and
  tests are deterministic.
- Lean's `stateAt` uses the same rule (`if t < seg.dur then ...`), so the fold selects the
  later phase at a boundary and returns `endState` at `t = totalTime`. Feasibility
  quantifies over `[0, total_time]`.
- `end_state` is computed by advancing through the segments; it is stored so callers do not
  re-fold it. `total_time` is the sum of durations.

### 3.7 Worked example (A reached, with cruise)

`A = 4`, `J = 2`, `V = 13`, `q0 = 0`, `q1 = 81.25`:

```
t_j = 2,  v_A = 8,  V ≥ v_A
d(V) = 13·(2 + 13/4)/2 = 34.125,  D_full = 68.25
D = 81.25 ≥ 68.25  → Case A
t_a = 13/4 − 2 = 1.25,  t_c = (81.25 − 68.25)/13 = 1
segments: (+2,2), (0,1.25), (−2,2), (0,1), (−2,2), (0,1.25), (+2,2)
total time = 11.5
```

This case is used in the golden corpus; every number is rational, so the expected segments
and sample states are exact.

### 3.8 Conservative rational template (M1-default)

The guaranteed Lean deliverable is a deliberately conservative planner with no radicals.
It is a valid jerk-limited rest-to-rest S-curve — triangular acceleration with an optional
cruise — and it uses the same 7-slot shape as §3.3, so everything downstream (profiles,
evaluation, stretch, sync, general planner) is unchanged.

Choose

```
τ = min 1 (min (A/J) (V/J))          -- τ > 0, and Jτ ≤ A, Jτ ≤ V
Δmin = 2 J τ³
```

For `Δ = q1 − q0 ≠ 0`, let `D = |Δ|`, `s = sign Δ`:

```
if D ≥ Δmin:
    j = J
    τ_c = (D − Δmin)/(J τ²)
else:
    j = D/(2 τ³)
    τ_c = 0

durations = (τ, 0, τ, τ_c, τ, 0, τ)
jerks     = (s·j, 0, −s·j, 0, −s·j, 0, s·j)
```

For `D = 0`, return the empty profile. Peak velocity is `j τ² ≤ J τ² ≤ V` (because
`Jτ ≤ V` and `τ ≤ 1`); peak acceleration is `j τ ≤ Jτ ≤ A`; the displacement is
`2jτ³ + jτ²τ_c = D`. When `j = J`, the profile cruises at `Jτ²`; when `j < J`, it is a
pure triangular move scaled to `D`.

Every duration and jerk is rational when the inputs are rational, and the planner uses
only `min`, comparison, multiplication and division — no `sqrt`/`cbrt`. It is therefore
generic over `Field` in Rust and exactly evaluable over `Ratio`. The Lean proofs are
`SegmentSafe` endpoint inequalities plus `ring`/`nlinarith` and one case split on
`D ≥ Δmin`. Its `PlanKind` is `Conservative`.

This is not the time-optimal 7-phase profile. That is M1-opt (§3.3), implemented in Rust
and golden-tested; its Lean proofs are staged, with Case A rational and Cases B/C radical.

## 4. Lean formalization

### 4.1 Core definitions

```lean
namespace Motion

structure Limits where
  vmax : ℝ
  amax : ℝ
  jmax : ℝ
  vmax_pos : 0 < vmax
  amax_pos : 0 < amax
  jmax_pos : 0 < jmax

structure State where
  q : ℝ
  v : ℝ
  a : ℝ

structure Segment where
  dur : ℝ
  dur_nonneg : 0 ≤ dur
  jerk : ℝ

structure Profile where
  start : State
  segments : List Segment
```

A segment's exit state and local state:

```lean
def Segment.stateAt (st : State) (s : Segment) (τ : ℝ) : State :=
  { q := st.q + st.v*τ + st.a*τ^2/2 + s.jerk*τ^3/6
    v := st.v + st.a*τ + s.jerk*τ^2/2
    a := st.a + s.jerk*τ }

def Segment.exit (st : State) (s : Segment) : State :=
  s.stateAt st s.dur
```

The profile fold extends the last segment's cubic past its end. This makes the profile
globally piecewise polynomial, so the gluing lemma applies on all of `ℝ` without
one-sided endpoint hypotheses:

```lean
def evalFrom (st : State) : List Segment → ℝ → State
  | [], _      => st
  | [s], t     => s.stateAt st t
  | s :: ss, t =>
      if t < s.dur then s.stateAt st t
      else evalFrom (s.exit st) ss (t - s.dur)

def Profile.stateAt (p : Profile) (t : ℝ) : State :=
  evalFrom p.start p.segments t
```

The singleton clause is deliberate: with a constant end-stub, a profile ending at nonzero
velocity would not be globally `C²` at `T`. Rust's `eval` clamps instead of extrapolating;
that divergence is documented in the Lean↔Rust map and only affects `t > totalTime`.

`Profile.totalTime` and `Profile.endState`:

```lean
def Profile.totalTime (p : Profile) : ℝ :=
  (p.segments.map Segment.dur).sum

def Profile.endState (p : Profile) : State :=
  p.segments.foldl Segment.exit p.start
```

`Feasible` is stated on the representation, not through a.e. derivatives:

```lean
def Profile.q (p : Profile) (t : ℝ) : ℝ := (p.stateAt t).q
def Profile.v (p : Profile) (t : ℝ) : ℝ := (p.stateAt t).v
def Profile.a (p : Profile) (t : ℝ) : ℝ := (p.stateAt t).a

-- The active segment's jerk under the later-segment rule; 0 for an empty profile.
def jerkAtFrom : List Segment → ℝ → ℝ
  | [], _      => 0
  | [s], _     => s.jerk
  | s :: ss, t => if t < s.dur then s.jerk else jerkAtFrom ss (t - s.dur)

def Profile.jerkAt (p : Profile) (t : ℝ) : ℝ := jerkAtFrom p.segments t

def Feasible (p : Profile) (lim : Limits) : Prop :=
  (∀ t ∈ Set.Icc 0 p.totalTime, |p.v t| ≤ lim.vmax) ∧
  (∀ t ∈ Set.Icc 0 p.totalTime, |p.a t| ≤ lim.amax) ∧
  (∀ s ∈ p.segments, s.dur > 0 → |s.jerk| ≤ lim.jmax)
```

The zero-duration guard in the jerk clause is deliberate: a zero-duration segment has no
open interval, so it is invisible to the a.e. third derivative; checking it would break
`feasible_iff_feasibleOn`. The planners emit zero-duration slots with `jerk ∈ {0, ±J}`,
which satisfy the bound anyway, so the guard costs nothing.

The composition and reparameterisation lemmas use a function-level predicate:

```lean
def FeasibleOn (f : ℝ → ℝ) (lim : Limits) (a b : ℝ) : Prop :=
  (∀ t ∈ Set.Ioo a b, |deriv f t| ≤ lim.vmax) ∧
  (∀ t ∈ Set.Ioo a b, |iteratedDeriv 2 f t| ≤ lim.amax) ∧
  (∀ᵐ t ∂(volume : Measure ℝ), t ∈ Set.Ioo a b →
    |iteratedDeriv 3 f t| ≤ lim.jmax)
```

Derivatives are quantified on the **open** interval: at the outer endpoints only one-sided
derivatives exist, and `deriv` on `Icc` would depend on an arbitrary extension. The state
fields are the polynomial derivatives, so `Feasible` can safely quantify them on `Icc`;
the lemma `feasible_iff_feasibleOn` connects the two via `p.q = fun t => (p.stateAt t).q`
and continuity at the boundaries. That bridge assumes `0 < totalTime` and the
zero-duration-guarded jerk clause above. `FeasibleOn` is vacuously true when `a = b`, so a
zero-total-time profile is judged by the state-level `Feasible` (which includes the
endpoint) or by adding endpoint bounds. The jerk clause of `Feasible` is the
representation-level version of the a.e. clause; `ae_iteratedDeriv_three_eq_jerk` is the
link.

A separate theorem links the segment jerk to the third derivative a.e.:

```lean
theorem ae_iteratedDeriv_three_eq_jerk (p : Profile) :
    ∀ᵐ t ∂(volume : Measure ℝ), t ∈ Set.Ioo 0 p.totalTime →
      iteratedDeriv 3 (fun t => (p.stateAt t).q) t = p.jerkAt t
```

`p.jerkAt t` is the jerk of the segment containing `t`; the theorem is a consequence of
the fold and the fact that the finite set of boundaries has measure zero. It is a
supporting theorem, not part of `Feasible`.

### 4.2 Structural lemmas (the reusable core)

These are proved once and used by every planner case:

```lean
-- fold / endpoint
theorem stateAt_zero (p) : p.stateAt 0 = p.start
theorem stateAt_totalTime (p) : p.stateAt p.totalTime = p.endState

def Profile.displacement : Profile → ℝ
  | ⟨st, []⟩     => 0
  | ⟨st, s::ss⟩  =>
      (st.v*s.dur + st.a*s.dur^2/2 + s.jerk*s.dur^3/6)
      + Profile.displacement ⟨s.exit st, ss⟩

theorem endState_q (p) : p.endState.q = p.start.q + p.displacement

-- concatenation
def Profile.append (p q : Profile) : Profile :=
  { start := p.start, segments := p.segments ++ q.segments }

theorem stateAt_append (p q) (h : q.start = p.endState) (ht : 0 ≤ t) :
  (p.append q).stateAt t =
    if t < p.totalTime then p.stateAt t
    else q.stateAt (t - p.totalTime)

theorem totalTime_append : (p.append q).totalTime = p.totalTime + q.totalTime
theorem feasible_append (h : q.start = p.endState)
    (hp : Feasible p lim) (hq : Feasible q lim) : Feasible (p.append q) lim

-- transforms
def Profile.translate (d : ℝ) (p : Profile) : Profile
def Profile.mirror (p : Profile) : Profile
def Profile.stretch (k : ℝ) (hk : 0 < k) (p : Profile) : Profile
def Profile.reverse (p : Profile) : Profile   -- optional normal form for start profiles

theorem feasible_translate / feasible_mirror / feasible_stretch / feasible_reverse
theorem stateAt_stretch (hk : 0 < k) :
  (stretch k p).stateAt (k*t) =
    { q := (p.stateAt t).q, v := (p.stateAt t).v / k, a := (p.stateAt t).a / k^2 }
theorem totalTime_stretch (hk : 0 < k) : (stretch k p).totalTime = k * p.totalTime
theorem stateAt_reverse (t ∈ Icc 0 p.totalTime) :
  (reverse p).stateAt t =
    { q := (p.stateAt (p.totalTime - t)).q,
      v := -(p.stateAt (p.totalTime - t)).v,
      a := (p.stateAt (p.totalTime - t)).a }
```

The derivative identities `deriv p.q = p.v` and `iteratedDeriv 2 p.q = p.a` are stated for
`p.segments ≠ []`. The empty profile is the constant start state; it is only used when
that state is a rest state, so the identity's exception is outside the planner's invariant.

`stretch` is deliberately defined with the scaled start state:

```lean
def Profile.stretch (k : ℝ) (hk : 0 < k) (p : Profile) : Profile :=
  { start := { q := p.start.q, v := p.start.v / k, a := p.start.a / k^2 }
    segments := p.segments.map fun s =>
      { dur := s.dur * k
        dur_nonneg := mul_nonneg (le_of_lt hk) s.dur_nonneg
        jerk := s.jerk / k^3 } }
```

The scaled start state is the correction to the draft. The state relation above is the
specification of what stretching means.

**Gluing lemma (corrected).** The draft's condition `∀ k < n` is off by one and the
statement is false: matching derivatives through order `n` is required for `C^n` gluing.
The correct statement, for globally smooth pieces, is

```lean
theorem contDiff_piecewise_le {n : ℕ} {f g : ℝ → ℝ} {c : ℝ}
    (hf : ContDiff ℝ n f) (hg : ContDiff ℝ n g)
    (h : ∀ k ≤ n, iteratedDeriv k f c = iteratedDeriv k g c) :
    ContDiff ℝ n (fun t => if t ≤ c then f t else g t)
```

Every piece of a profile is a cubic, hence `ContDiff ℝ ⊤`; the fold supplies the matching
value, velocity and acceleration at each junction by construction. The proof is induction
on `n` using `HasDerivWithinAt.union` at the junction and `contDiff_succ_iff_deriv`
(see §4.7 for the Mathlib specifics). The one-sided derivative version is unnecessary for
polynomial segments; do not build it.

`Profile.evalFrom`'s singleton clause makes the tail a global polynomial, so
`ContDiff ℝ 2 p.q` follows from this lemma without interval-endpoint case analysis.
`FeasibleOn` still quantifies over `[0, totalTime]`; the extension past `T` is an
evaluation convenience, and Rust clamps there.

### 4.3 Segment safety: the bridge from arithmetic to `Feasible`

The planner's case proofs all reduce to one local lemma. Define

```lean
def SegmentSafe (st : State) (s : Segment) (lim : Limits) : Prop :=
  |st.v| ≤ lim.vmax ∧ |st.a| ≤ lim.amax ∧ |s.jerk| ≤ lim.jmax ∧
  |(s.exit st).v| ≤ lim.vmax ∧ |(s.exit st).a| ≤ lim.amax ∧
  0 ≤ st.a * (s.exit st).a
```

The last clause says the acceleration does not change sign inside the segment. Since
`a(τ)` is linear between `st.a` and `(s.exit st).a`, it lies between the endpoints, so
`|a(τ)| ≤ max(|st.a|, |exit.a|) ≤ A`. Since `a` has one sign, `v(τ) − v(0)` and
`v(dur) − v(τ)` are integrals of a function of one sign, so `v` lies between its endpoints
and `|v(τ)| ≤ max(|st.v|, |exit.v|) ≤ V`.

```lean
theorem segmentSafe_bounds (h : SegmentSafe st s lim) :
  ∀ τ ∈ Set.Icc 0 s.dur,
    |(s.stateAt st τ).v| ≤ lim.vmax ∧ |(s.stateAt st τ).a| ≤ lim.amax
```

The bridge to a whole profile is a recursive predicate:

```lean
def SafeFrom (lim : Limits) (st : State) : List Segment → Prop
  | []      => |st.v| ≤ lim.vmax ∧ |st.a| ≤ lim.amax
  | s :: ss => SegmentSafe st s lim ∧ SafeFrom lim (s.exit st) ss

theorem feasible_of_safeFrom {p : Profile} (h : SafeFrom lim p.start p.segments) :
  Feasible p lim
```

The nil case is load-bearing: an empty profile still has `t = 0` in `Icc 0 0`, so its
start state must satisfy the velocity and acceleration bounds. Allowing `True` there would
make `plan_general`'s empty stop/mid/start pieces unsound.
This is the main reason the phase lists of §3.3 keep the adjacent `−J` phases separate:
every segment has a single acceleration sign, so the local proof applies without finding
an interior velocity maximum.

**M3 — stretching and synchronisation**

A `JointProfile` carries the common duration in its type, so "all joints finish together"
is a field, not a side condition:

```lean
structure JointProfile (n : ℕ) where
  profiles : Fin n → Profile
  duration : ℝ
  duration_nonneg : 0 ≤ duration
  same_duration : ∀ i, (profiles i).totalTime = duration

noncomputable def syncTime {n} (p : Fin n → Profile) : ℝ :=
  (List.ofFn fun i => (p i).totalTime).foldr max 0
```

`foldr max 0` handles `n = 0` without a `Nonempty` instance and avoids relying on an order
bottom for `ℝ`, which `Finset.sup` would need.

Zero-total-time joints need a hold, not a division by zero:

```lean
def hold (q T : ℝ) (hT : 0 ≤ T) : Profile :=
  { start := ⟨q, 0, 0⟩, segments := [⟨T, hT, 0⟩] }

noncomputable def stretchTo (T : ℝ) (p : Profile) (hT : 0 ≤ T)
    (hle : p.totalTime ≤ T) : Profile :=
  if h0 : p.totalTime = 0 then hold p.start.q T hT
  else
    have hp : 0 < p.totalTime := lt_of_le_of_ne (totalTime_nonneg p) (Ne.symm h0)
    have hTpos : 0 < T := lt_of_lt_of_le hp hle
    stretch (T / p.totalTime) (div_pos hTpos hp) p
```

`stretchTo` is used with `p.totalTime ≤ T`. Under that hypothesis the factor is at least
one, so `stretch_feasible` applies; the zero-total-time branch is a constant hold. The
hold is deliberate: `JointProfile` asserts one common duration for every joint, so a
zero-motion joint is represented as "already at target, held for the move" rather than as
an exception with total time zero. That keeps `same_duration` total and makes evaluation
at every `t ∈ [0, T]` well-defined for all joints.

```lean
noncomputable def synchronize {n} (p : Fin n → Profile) : JointProfile n :=
  { profiles i :=
      stretchTo (syncTime p) (p i) (syncTime_nonneg p) (totalTime_le_syncTime p i)
    duration := syncTime p
    duration_nonneg := syncTime_nonneg p
    same_duration i := stretchTo_totalTime (p i) (totalTime_le_syncTime p i) }
```

| Theorem | Statement |
| --- | --- |
| `stretch_feasible` | `k ≥ 1 → Feasible p lim → Feasible (stretch k p) lim` |
| `stretch_isRest` | `IsRest p → IsRest (stretch k p)` |
| `stretch_totalTime` | `(stretch k p).totalTime = k * p.totalTime` |
| `stateAt_stretch` | the state relation of §4.2 |
| `stretchTo_totalTime` | `p.totalTime ≤ T → (stretchTo T p).totalTime = T` |
| `stretchTo_feasible` | `p.totalTime ≤ T → Feasible p lim → Feasible (stretchTo T p) lim` |
| `stretchTo_endpoints` | start and end positions are preserved; rest boundaries stay rest |
| `totalTime_le_syncTime` | `(p i).totalTime ≤ syncTime p` |
| `syncTime_nonneg` | `0 ≤ syncTime p` |
| `synchronize_feasible` | each joint feasible → each synchronised joint feasible |
| `synchronize_isRest` | each joint `IsRest` → each synchronised joint `IsRest` |
| `synchronize_totalTime` | every joint's total time is the common `duration` |
| `synchronize_endpoints` | under `IsRest`, each synced joint still starts and ends at its original positions |
| `synchronize_rest_to_rest` | under `IsRest`, rest boundary conditions are preserved |

| `synchronize_all_zero` | `syncTime = 0`, duration zero, all coordinates constant |
| `synchronizedStop_rest_at_Tmax` | every joint's stop+hold profile has `v = a = 0` at `T_max` |
| `synchronizedStop_totalTime` | every joint's stop+hold profile has total time `T_max` |

`sync` requires `IsRest`:

```lean
def IsRest (p : Profile) : Prop :=
  p.start.v = 0 ∧ p.start.a = 0 ∧ p.endState.v = 0 ∧ p.endState.a = 0
```

`IsRest` is defined using the state fields. A zero-total-time profile is a constant
trajectory: `stateAt` returns its start for every `t`, so it cannot consistently carry a
nonzero `v` or `a` as a derivative. The planners satisfy this invariant by construction —
any nonzero boundary velocity or acceleration forces a positive-duration ramp — and the
sync `hold` is only used for `IsRest` profiles. Do not construct a zero-duration profile
with nonzero state fields by hand.

Stretching preserves only rest boundary conditions. A general profile with nonzero start
velocity is not synchronisable by stretching: the stretched start velocity would be
`v0/k`, not the measured `v0`. This is why M3 is rest-to-rest and why multi-joint re-plan
from a moving state uses a synchronised stop followed by a MoveJ (§2, §5.4).

**Two MoveJ semantics.** The six-profile `synchronize` above preserves each joint's own
profile shape, but the induced joint-space path `t ↦ (q_i(t))` is not the straight line
`q0 + s (q1 − q0)` unless all six profiles happen to be proportional. If the standard
industrial MoveJ semantics is wanted — a straight line in joint space — use the scalar
variant instead:

```lean
-- q_i(t) = q0_i + s(t) * Δq_i, with one profile s : [0,T] → [0,1].
-- Effective limits over joints with Δq_i ≠ 0:
--   Vs = min_i vmax_i / |Δq_i|
--   As = min_i amax_i / |Δq_i|
--   Js = min_i jmax_i / |Δq_i|
noncomputable def movejScalar (q0 q1 : Fin n → ℝ) (lim : Fin n → Limits) : Profile
```

`movejScalar` is `planRestConservative 0 1 ⟨Vs,As,Js⟩` by default (the verified template);
the optimal `planRestToRest` can be substituted once M1-opt is accepted. Then
`q_i(t) = q0_i + Δq_i s(t)`. If every `Δq_i = 0`, the moving-joint set is empty: return the
zero-motion profile (empty, total time 0) and do not compute `Vs/As/Js`; `q0 = q1`, so the
boundary and feasibility theorems hold trivially.
The theorems are direct instances of the 1-DOF results:

| Theorem | Statement |
| --- | --- |
| `movejScalar_feasible` | the induced joint trajectory respects every joint's limits |
| `movejScalar_path` | `q_i(t) = q0_i + (q1_i − q0_i) s(t)`; the path is a joint-space line |
| `movejScalar_boundary` | `q(0) = q0`, `q(T) = q1`, rest at both ends |

This mode is less proof work than `synchronize` and gives a stronger path guarantee. It is
the recommended primary MoveJ; `synchronize` remains the mode for per-joint profile shapes.
In Lean, `movejScalar` returns the scalar `s`-profile and `movejScalar_path` states the
induced joint trajectory; in Rust, `plan_movej_scalar` materialises the per-joint
`Profile`s (each segment's jerk multiplied by `Δq_i`) so the caller can evaluate joints
directly.

**Synchronised stop (re-plan from motion).** `synchronize` cannot stop a moving arm: it
requires `IsRest`, and stretching a stop profile changes its start velocity. Define a
separate construction:

1. For each joint, `stop_profile(measured_i, lim_i)` ends at rest.
2. `T_max = max_i (stop_profile_i).totalTime`.
3. Append a zero-jerk `hold` of duration `T_max − T_i` to each stop profile. Every joint
   now has total time `T_max` and ends at rest. This is a `JointProfile` whose common
   duration is `T_max`; the per-joint profiles are not stretched, so their start states
   are the measured states.
4. From the stopped positions, run MoveJ-scalar (or `synchronize`) to the target.

The construction is a supervisor policy, not a variant of `synchronize`. Its proof
obligations are `stopProfile_ends_at_rest`, `hold` feasibility, and `totalTime` arithmetic;
add `synchronizedStop_rest_at_Tmax` / `synchronizedStop_totalTime` to the M3 table and a
matching test.

**Master composition lemma (used by the supervisor and by M5)**

One chain-rule lemma serves both the time-scaling supervisor and the Cartesian refinement.
Prove it once, independently of the planner:

```lean
theorem comp_bounds
  (f σ : ℝ → ℝ) {a b : ℝ}
  (M1 M2 M3 S1 S2 S3 L1 L2 L3 : ℝ)
  (hf : ContDiffOn ℝ 3 f (Set.Ioo a b))
  (hσ : ContDiffOn ℝ 3 σ (Set.Ioo a b))
  (hσmaps : Set.MapsTo σ (Set.Ioo a b) (Set.Ioo a b))
  (hf1 : ∀ t ∈ Set.Ioo a b, |deriv f t| ≤ M1)
  (hf2 : ∀ t ∈ Set.Ioo a b, |iteratedDeriv 2 f t| ≤ M2)
  (hf3 : ∀ t ∈ Set.Ioo a b, |iteratedDeriv 3 f t| ≤ M3)
  (hs1 : ∀ t ∈ Set.Ioo a b, |deriv σ t| ≤ S1)
  (hs2 : ∀ t ∈ Set.Ioo a b, |iteratedDeriv 2 σ t| ≤ S2)
  (hs3 : ∀ t ∈ Set.Ioo a b, |iteratedDeriv 3 σ t| ≤ S3)
  (h1 : M1 * S1 ≤ L1)
  (h2 : M2 * S1^2 + M1 * S2 ≤ L2)
  (h3 : M3 * S1^3 + 3 * M2 * S1 * S2 + M1 * S3 ≤ L3) :
  (∀ t ∈ Set.Ioo a b, |deriv (fun t => f (σ t)) t| ≤ L1) ∧
  (∀ t ∈ Set.Ioo a b, |iteratedDeriv 2 (fun t => f (σ t)) t| ≤ L2) ∧
  (∀ t ∈ Set.Ioo a b, |iteratedDeriv 3 (fun t => f (σ t)) t| ≤ L3)
```

The chain-rule identities are `(f∘σ)' = f'σ'`,
`(f∘σ)'' = f''(σ')² + f'σ''`, and
`(f∘σ)''' = f'''(σ')³ + 3f''σ'σ'' + f'σ'''`. Mathlib v4.35 has
`iteratedDeriv_comp_two` and `iteratedDeriv_comp_three` in
`Mathlib/Analysis/Calculus/IteratedDeriv/FaaDiBruno.lean`; the proof is the triangle
inequality after those rewrites.

`hσmaps` is necessary, not decorative: the derivative bounds are only known on `(a,b)`,
while the chain rule evaluates them at `σ t`. Without `σ(Ioo a b) ⊆ Ioo a b` the statement
is false (take `f` vanishing on `(-∞,1]` and `σ t = t+10` on `(0,1)`). The supervisor's
affine clock `σ(t)=t/k` maps `(0,b)` into `(0,b)` for `k ≥ 1`; the Cartesian instance
carries the same condition as `hsmap`.

Apply `comp_bounds` on an open interval where both `f` and `σ` are `C³`; for a profile,
that is the interior of one segment, and the endpoint bounds follow by continuity. The
third derivative of a profile does not exist at jerk boundaries, which is why `FeasibleOn`
states the jerk clause almost everywhere and the composition theorem is applied piecewise.
For an affine clock the derivatives are global.

- **Supervisor instance:** `f = p.q`, `M_i = L_i = lim` and `σ` is the reference clock.
  The lemma says the scaled reference is feasible when the clock bounds satisfy the three
  inequalities. For an affine clock (`σ(t)=t/k`, `S1=1/k`, `S2=S3=0`) the inequalities are
  `v/k ≤ v`, `a/k² ≤ a`, `j/k³ ≤ j`, which hold for `k ≥ 1`; this is `stretch_feasible`.
  A non-affine clock must supply `S2`, `S3` and a rate limiter; a rate that changes
  instantaneously does not satisfy the hypotheses. M4 therefore changes rate only at cycle
  boundaries and claims feasibility per constant-rate interval, not `C²` continuity of the
  concatenated reference.
- **Cartesian instance:** `f = Q_i` (the `i`-th joint coordinate along the path),
  `M = (M1_i, M2_i, M3_i)` are the path derivative bounds, `σ = s` is the path clock with
  `(S1,S2,S3) = (V,A,J)`, and `L = (v_i,a_i,j_i)` are the joint limits. The three
  inequalities are exactly the certificate of the next section.

**M5 — Cartesian certification**

The theorem is conditional and does not mention IK by name. It composes per-joint path
bounds with the clock bounds via `comp_bounds`:

```lean
theorem cartesian_path_feasible
  (q : ℝ → Fin n → ℝ) (s : ℝ → ℝ) (lim : Fin n → Limits) {T : ℝ}
  (M1 M2 M3 : Fin n → ℝ)
  (hT : 0 < T)
  (hQ : ∀ i, ContDiffOn ℝ 3 (fun s => q s i) (Set.Ioo 0 1))
  (hs : ContDiffOn ℝ 3 s (Set.Ioo 0 T))
  (hsmap : Set.MapsTo s (Set.Ioo 0 T) (Set.Ioo 0 1))
  (hQ1 : ∀ i t ∈ Set.Ioo 0 1, |deriv (fun s => q s i) t| ≤ M1 i)
  (hQ2 : ∀ i t ∈ Set.Ioo 0 1, |iteratedDeriv 2 (fun s => q s i) t| ≤ M2 i)
  (hQ3 : ∀ i t ∈ Set.Ioo 0 1, |iteratedDeriv 3 (fun s => q s i) t| ≤ M3 i)
  (hs1 : ∀ t ∈ Set.Ioo 0 T, |deriv s t| ≤ V)
  (hs2 : ∀ t ∈ Set.Ioo 0 T, |iteratedDeriv 2 s t| ≤ A)
  (hs3 : ∀ t ∈ Set.Ioo 0 T, |iteratedDeriv 3 s t| ≤ J)
  (hvel : ∀ i, M1 i * V ≤ (lim i).vmax)
  (hacc : ∀ i, M2 i * V^2 + M1 i * A ≤ (lim i).amax)
  (hjerk : ∀ i, M3 i * V^3 + 3 * M2 i * V * A + M1 i * J ≤ (lim i).jmax) :
  (∀ i t ∈ Set.Ioo 0 T, |deriv (fun t => q (s t) i) t| ≤ (lim i).vmax) ∧
  (∀ i t ∈ Set.Ioo 0 T, |iteratedDeriv 2 (fun t => q (s t) i) t| ≤ (lim i).amax) ∧
  (∀ i t ∈ Set.Ioo 0 T, |iteratedDeriv 3 (fun t => q (s t) i) t| ≤ (lim i).jmax)
```

The proof is `comp_bounds` instantiated per joint. The theorem is stated for a clock that
is genuinely `C³` on `(0,T)`. A 7-slot profile is `C³` on each segment interior but only
`C²` at a jerk junction, so do **not** instantiate the pointwise `hσ`/`hs3` hypotheses at a
junction: apply the theorem on each open segment, extend the velocity and acceleration
bounds to the junction by continuity, and use the a.e. jerk statement (`FeasibleOn`'s
third clause). The junction set is finite, hence measure zero. If a globally `C³` clock is
wanted instead, smooth the profile's rate explicitly before applying the theorem.

`hQ` is the trusted smooth-branch assumption. `hsmap` follows from the rest-to-rest
`s`-profile's no-overshoot theorem (`s` stays in `[0,1]`). The a.e. jerk bound is the
profile's per-segment jerk bound, transferred by `ae_iteratedDeriv_three_eq_jerk`.

The planner supplies `s` as a rest-to-rest profile in the path parameter with limits
`(V,A,J)`:

```
V ≤ min_i v_i / M1_i
A ≤ min_i (a_i − M2_i V²) / M1_i
J ≤ min_i (j_i − M3_i V³ − 3 M2_i V A) / M1_i
```

over joints with `M1_i > 0`. The computation is **sequential**: choose `V`, then `A`
using that `V`, then `J` using both. If any numerator is non-positive, no positive `A` or
`J` exists under this conservative scheme: the certifier returns a typed error rather than
a slower profile. Joints with `M1_i = 0` are frozen along the path and impose no velocity
constraint; if every joint has `M1_i = 0` the path is stationary and should be handled as a
zero-motion request. `PlanError::PositionLimit` is only produced when a caller-supplied
`PositionLimits` is present; the core certifier does not define position limits. The theorem's `∀ t` hypotheses are read on the interval where the clock is
defined; when `s` is a profile, apply `comp_bounds` on each segment interior and extend by
continuity, exactly as in §4.4.

This is **feasibility-first, not TOPP**. It is slower than a state-dependent time-optimal
parameterisation, and it may reject paths that a TOPP solver could time. That is the
honest boundary. True TOPP — state-dependent constraints, bang-bang switching, numerical
integration — is deferred and is not a reuse of `planRestToRest`.

Why a Jacobian bound is not enough: `q'(s) = J^{-1} C'(s)` depends on `‖J^{-1}‖`
(a lower bound on `σ_min(J)`, not an upper bound on `‖J‖`); `q''(s)` depends on
`dJ/ds`, hence on the Hessian of FK; `q'''(s)` depends on `d²J/ds²`. The theorem is
therefore stated with the per-joint path bounds `M1/M2/M3`, which are what the certifier
must supply. The Jacobian is the computational route to those bounds, not the hypothesis.

The repository has no Jacobian today. M5 therefore includes a new analytic
Jacobian/path-derivative layer in `robot-kinematics`, cross-checked against finite
differences, before the certifier can be built. That layer is a prerequisite for M5 and is
not part of M1–M4.

Trusted assumptions, stated in `docs/verification.md`:

1. `C : [0,1] → Pose` is `C³` and its rotation part is a rotation.
2. One IK branch is fixed and continuous along the path; `fk (q(s)) = C(s)`; no branch,
   elbow, wrist or representative switch. The `nearestRepresentative`/`turnIndex` layer of
   `Atan2.lean` is used to lift angles continuously; a wrapped canonical representative
   would appear as a full-turn jump.
3. `σ_min(J(q(s))) ≥ m > 0` with margin along the path (sampled; abort otherwise).
4. `M1/M2/M3` bound the path derivatives on the whole path, not merely at samples. The
   Rust certifier samples adaptively and adds a Lipschitz margin where possible; it says
   in the test and in the docs that this is a numerical certificate, not a proof.
5. The clock bounds `(V,A,J)` and rest-to-rest `s`-boundary conditions hold.

The runtime certifier fails closed: every division, linear solve and inverse-trig call is
guarded; a branch switch, singularity, position-limit violation, non-positive certificate
denominator, or non-finite value yields a typed error (`Singularity`, `BranchSwitch`,
`PositionLimit`, `Uncertifiable`, `InfeasibleUnderConservativeBounds`) and holds position.
It never passes NaN to a joint. Abort cases are acceptance tests, not error-handling
afterthoughts.

### 4.5 Proof strategy and dependencies

1. **Motion.Basic.** Definitions; `stateAt` fold lemmas; `append`, `translate`, `mirror`,
   `stretch`, `reverse`; `Feasible`; `SegmentSafe`; `segmentSafe_bounds`; `SafeFrom`
   induction. This is the foundation and should be merged before planner case proofs.
2. **Motion.Glue.** The corrected global piecewise lemma of §4.2, then the planner
   smoothness theorems by induction over segments with the shifted tail composed by
   `ContDiff.comp` (`planRestConservative_smooth` first, then `planRestToRest_smooth`).
   Each phase is a polynomial, hence globally `C∞`; at a junction the fold's state
   equality gives matching value, first and second derivatives.
   Use `Polynomial.hasDerivAt_aeval`, `Polynomial.deriv_aeval` and
   `Polynomial.contDiff_aeval` for the cubic derivative lemmas — **`fun_prop` does not
   prove `HasDerivAt` goals** and is not a substitute here. Keep this file separate from
   the planner so a Mathlib workaround does not block arithmetic.
3. **Motion.Plan.** Two planners share the structural layer:
   - `Plan/Conservative.lean`: the M1-default rational template (§3.8). Small, no
     radicals; prove it first.
   - `Plan/Common.lean`, `Plan/Full.lean`, `Plan/NoCruise.lean`, `Plan/Triangular.lean`:
     the M1-opt 7-phase planner (§3.3), staged behind the conservative milestone.
   The case proofs use `SegmentSafe`. Split the M1-opt cases into separate files if
   several agents work in parallel. The a.e. third-derivative bridge is a separate small
   file: the junction set is finite (prefix sums of durations), so
   `Set.Finite.measure_zero` (import `Mathlib.MeasureTheory.Measure.Typeclasses.NullSingletonClass`)
   gives the measure-zero statement. Do **not** state a pointwise `iteratedDeriv 3` bound
   at a jerk junction; Lean's `deriv` there is a junk value.
4. **Motion.General.** Stop/brake/start profiles; `stopFeasible`; `planGeneral`;
   the endpoint and rejection theorems. Depends on rest-to-rest for the middle.
5. **Motion.Compose.** `comp_bounds`; independent of the planner and reusable by the
   supervisor and M5.
6. **Motion.Sync.** `IsRest`, `syncTime`, `hold`, `stretchTo`, `synchronize`, and the M3
   table. Depends only on the stretch lemmas from `Basic`.
7. **Motion.MoveJ.** `movejScalar` and its three theorems; depends on `Plan` and `Basic`.
8. **Motion.Cartesian.** Optional; `cartesian_path_feasible` via `comp_bounds`; depends on
   `Compose` and is independent of the planner proofs.

The planner arithmetic is the long pole, not the definitions. The case proofs are
mechanical once `SegmentSafe` exists: unfold the emitted list, discharge each segment's
endpoint inequalities with `nlinarith`/`positivity`/`field_simp`, and use the defining
equation of `t_r`, `t_a`, `t_c` or `v_p` to close the displacement sum.

### 4.7 Proof risks and fallbacks

**Scope decision: M1-default is the conservative rational template; M1-opt is the
7-phase optimal planner.** The conservative template of §3.8 is fully proved in Lean, is
generic over `Field` in Rust, and is exactly testable over `Ratio`. It is the default used
by M2–M4. The 7-phase closed form of §3 is the product-target optimal planner, labeled
M1-opt. Its radical cases are the Lean long pole: Case A with `A` reached is rational, but
the triangular-cruise case, Case B and Case C need `sqrt`/`cbrt`, and Mathlib has no
`Real.cbrt` (only `Real.rpow x (1/3)`). M1-opt is therefore staged and **not a gate** for
M1:
- **M1-opt A:** Lean proofs for the rational-only Case A with `A` reached; Rust optimal
  planner; golden cases.
- **M1-opt A′/B/C:** Lean proofs for the triangular-cruise case, Case B and Case C, using
  `Real.sqrt`/`Real.rpow` and the defining equations (`v_p²/A + v_p t_j = D`,
  `2J t_r³ = D`) rather than a numerical root solver. This is the 4–8 week risk; it does
  not block M2–M4.
- The Rust `plan_rest_to_rest` implements the optimal planner and is tested against the
  exact rational constructions of §6 with a declared tolerance. The verified
  `plan_rest_conservative` remains available as the fallback and as the M1 spec.
If M1-opt A′/B/C is not completed, the gap is named in `docs/lean-rust-map.md`; no claim
about the optimal planner's Lean proof is implied.

Proof risks, in descending order:

- **Optimal radical cases (A′/B/C).** These are the schedule risk for M1-opt. `Real.sqrt`
  is available; `Real.cbrt` is not, so Case C uses `Real.rpow x (1/3)`. Prove the defining
  equations (`v_p²/A + v_p t_j = D`, `2J t_r³ = D`) rather than any numerical root
  property. M1-opt is explicitly non-gating: the conservative M1-default is the verified
  planner, and the Rust optimal planner is golden-tested regardless.
- **Gluing API.** Mathlib has no ready piecewise-`C²` lemma (`ContDiffOn.union_of_isOpen`
  requires open sets). The corrected `contDiff_piecewise_le` of §4.2 is proved by
  induction and compiled in a scratch file; use it. Do not use the draft's `k < n`
  version, which is false.
- **Cube root.** `Real.rpow x (1/3)` is the intended definition. The proof obligation is
  `t_r^3 = D/(2J)` for `t_r ≥ 0`; `Real.rpow_mul` and `Real.rpow_natCast` supply it. If
  the algebra is awkward, define `triRamp` by `Classical.choose` from an
  existence/uniqueness lemma for `t ↦ t³` and project the defining equation; the planner
  only needs the spec equation, not a computable root.
- **Fold/junction localization.** Proving that strictly inside a segment the fold equals
  the cubic, and that the junction set is exactly the prefix sums, is the main
  bookkeeping work. Zero-duration segments make repeated cumulative times; the `Finset`
  collapses them, which is the intended behavior.
- **Displacement sums.** Use a `Profile.displacement` fold lemma and rewrite each case to
  the corresponding `d(v)` identity. Do not expand every cubic by hand in the top-level
  theorem; prove one lemma per case shape.
- **Necessity in M2.** `stopFeasible_necessary` reasons about an arbitrary profile. If the
  integral/velocity argument is costly, land `planGeneral_isSome_iff` as the two
  constructive directions plus `none_of_not_stopFeasible` for the initial-state condition
  and document the target-state half as a proof gap. The runtime rejection is unaffected.
- **`fun_prop` does not prove `HasDerivAt`.** Use the polynomial API
  (`Polynomial.hasDerivAt_aeval`, `deriv_aeval`, `contDiff_aeval`) or explicit
  `hasDerivAt` combinators; do not spend time on `fun_prop` for derivative goals.
- **Lean extrapolates, Rust clamps.** `evalFrom` extends the last cubic past `T`; Rust's
  `eval` clamps. The divergence is outside `[0,T]` and documented in the map; golden
  samples stay inside the interval.

```rust
pub struct Profile<S = f64> {
    /* start, end, segments: [Segment<S>; MAX_PHASES],
       starts: [State<S>; MAX_PHASES], len, total_time, kind */
}

impl<S: Field> Profile<S> {
    pub fn from_parts(start: State<S>, segments: &[Segment<S>])
        -> Result<Self, ProfileError>;
    pub fn try_push(&mut self, seg: Segment<S>) -> Result<(), ProfileError>;
    pub fn start(&self) -> State<S>;
    pub fn end(&self) -> State<S>;
    pub fn total_time(&self) -> S;
    pub fn kind(&self) -> PlanKind;
    pub fn segments(&self) -> &[Segment<S>];
    pub fn phase_start(&self, index: usize) -> Option<State<S>>;
    /// Clamps to [0, total_time]; selects the later segment at a boundary.
    pub fn eval(&self, t: S) -> State<S>;
    /// Reference at scaled progress `s` with clock rate `rate` and rate derivative
    /// `rate_dot`; the supervisor uses `rate_dot = 0` and a constant rate per cycle.
    pub fn eval_scaled(&self, s: S, rate: S, rate_dot: S) -> State<S>;
    pub fn stretch(&self, factor: S) -> Result<Self, ProfileError>;
    pub fn translate(&self, dq: S) -> Self;
    pub fn mirror(&self) -> Self;
    /// Concatenate; `next.start` must equal `self.end`.
    pub fn append(&self, next: &Profile<S>) -> Result<Self, ProfileError>;
    /// Time reversal; starts at `self.end` with velocity negated.
    pub fn reverse(&self) -> Self;
}

/// Verified default: the conservative rational template of §3.8.
/// Generic over `Field`, so `Ratio` runs the same code exactly.

pub fn stop_feasible(state: State<f64>, lim: Limits<f64>) -> bool;

}

```

`plan_movej_scalar_optimal` shares the effective-limit computation and the per-joint
scaling with `plan_movej_scalar`; only the scalar profile constructor differs. The
conservative template is still the verified default, but its duration has a floor of
`4·min(1, A/J, V/J)` — four seconds for any non-zero move under typical limits — so the
interactive app uses the optimal one.

Error types are closed enums: `PlanError::{NonPositiveLimit, NonFiniteInput, Infeasible,
NumericalFailure, ProfileOverflow}`; `ProfileError::{TooManySegments, NegativeDuration,
NonFinite, InvalidStretch}`. They implement `Display` and `core::error::Error` without
allocation. No `unwrap` on a control path.

`plan_rest_conservative` and `plan_rest_to_rest` fail on non-finite inputs, and on finite
inputs whose derived quantities overflow to a non-finite value (`NumericalFailure`). For
finite inputs whose derived quantities stay finite and valid limits, they return `Ok`. The
conservative planner is the verified default and is generic over `Field`; the optimal
planner is f64 and is M1-opt. `plan_general` returns `Err(PlanError::Infeasible)` exactly
when `Viable` fails. `Profile::try_push` is checked so a planner bug cannot panic; the
planner's construction is bounded by 15 and is tested at that bound.

`synchronize` requires rest-to-rest profiles. A `RestProfile` newtype with a checked
constructor is recommended; at minimum the function documents the precondition and has a
debug assertion. The Lean `IsRest` predicate is the specification counterpart.

`eval` uses the later-segment rule at boundaries and clamps outside `[0, T]`, matching
§3.6. `stretch` rejects `factor < 1` and non-finite factors; Lean's `stretch` is defined
for any `k > 0`, so the Rust domain is deliberately narrower (the supervisor only needs
`k ≥ 1`). The Lean↔Rust map records the difference. The supervisor uses
`eval_scaled(s, rate, rate_dot)` and never claims a `C²` concatenation.

### 5.3 Planner implementation

`src/conservative.rs` mirrors `Motion/Plan/Conservative.lean`:

- `τ = min 1 (min (A/J) (V/J))`, `Δmin = 2Jτ³`.
- `D = 0` returns the empty profile before any division.
- If `D ≥ Δmin`: `j = J`, `τ_c = (D − Δmin)/(Jτ²)`.
- If `D < Δmin`: `j = D/(2τ³)`, `τ_c = 0`.
- The 7-slot list `(τ,0,τ,τ_c,τ,0,τ)` with jerks `(j,0,−j,0,−j,0,j)` and direction sign.
- It is generic over `Field`: no `sqrt`/`cbrt`, so `plan_rest_conservative::<Ratio>` is
  exact and the golden tests compare its output with `==`.
- No `unwrap` on user-controlled data; limits are validated at construction.

`src/plan.rs` mirrors `Motion/Plan.lean` (M1-opt):

- `d(v)` and `D_full(V)` with the `v ≤ A²/J` split.
- Case selection in the order of §3.4: zero motion, cruise at `V`, no-cruise with `A`
  reached, triangular.
- The same 7-slot shape; zero-duration slots retained, matching the Lean list.
- `mirror` for `q1 < q0`; `translate` for `q0`.
- Stable formulas: compute `v_A = A²/J` once and use `v_A² + 4 A D` for the Case B
  discriminant; compute the triangular root as
  `u = cbrt(D * sqrt(J) / 2)`, `v_p = u²`, `t_r = u / sqrt(J)`.

`src/general.rs` mirrors `Motion/General.lean`: `rev`, `stop_feasible`, `stop_profile`,
`start_profile`, `append`, `plan_general`. The middle uses `plan_rest_conservative` by
default, matching the Lean proof; the optimal planner can be substituted once M1-opt is
accepted. The f64 implementation concatenates the three segment lists directly rather than
using `Profile::append`'s exact junction check: the intermediate positions can differ by
rounding, while the junction velocities and accelerations are zero. `append` remains the
exact-rational/API operation and is tested over `Ratio`. `append` returns `Result` if
capacity would be exceeded; the general planner's construction stays within 15 by the
bound in §3.5.

### 5.4 Tracker and supervisor

The tracker is deliberately simple and plant-agnostic. It outputs an acceleration command
and a saturation flag; the plant decides what that means:

```rust
pub struct TrackingGains { pub kp: f64, pub kd: f64, pub max_accel: f64 }
pub struct Command { pub accel: f64, pub saturated: bool }

pub struct Tracker { gains: TrackingGains }

impl Tracker {
    /// a_cmd = a_ref + kp e + kd e_dot, clamped to ±max_accel.
    /// The clamp is written explicitly, not with f64::clamp, which panics on NaN.
    pub fn command(&self, reference: State<f64>, measured: State<f64>) -> Command;
}
```

The supervisor's verified contract is narrow and explicit:

```rust
pub struct SupervisorConfig {
    pub eps_1: f64,        // no slowdown below this error
    pub eps_2: f64,        // full stop above this error
    pub eps_abort: f64,    // persistent-error abort threshold
    pub abort_cycles: u32,
    pub stall_cycles: u32,
    pub stall_velocity: f64,
    pub cycle: f64,
}

pub enum Decision {
    Tracking,
    Slowing,               // rate is SupervisorStep.rate, in [0, 1]
    Holding,
    Replan,
    Stall,
    Complete,
    Abort,
}

pub struct SupervisorStep { pub decision: Decision, pub rate: f64,
                             pub reference_time: f64 }

pub struct Supervisor<const N: usize> { /* config, s, per-joint counters */ }

impl<const N: usize> Supervisor<N> {
    pub fn new(config: SupervisorConfig) -> Self;
    /// Restart the reference clock and clear per-joint counters after a re-plan.
    pub fn reset(&mut self, reference_time: f64);
    pub fn step(
        &mut self,
        errors: &[f64; N],
        velocities: &[f64; N],
        commands: &[Command; N],
        total_time: f64,
    ) -> SupervisorStep;
}
```

The rate law is the draft's piecewise-linear slowdown, with `rate` held constant within a
cycle and changed only at cycle boundaries. `eval_scaled(s, rate, rate_dot)` is the
reparameterised reference state

```
q = p.q(s)
v = p.v(s) · rate
a = p.a(s) · rate² + p.v(s) · rate_dot
```

The supervisor uses `rate_dot = 0`. Between rate changes this is an affine
reparameterisation with `k = 1/rate ≥ 1`, so `stretch_feasible` applies. At a rate change
the velocity setpoint may step; the tracker absorbs it. No theorem claims `C²` continuity
of the concatenated reference. If smooth rate modulation is wanted later, it must use
`comp_bounds` with explicit `clock_accel_max` and `clock_jerk_max` and a slew limiter.

Supervisor decision priority: `Stall > Replan > Abort > Complete > Holding > Slowing >
Tracking`. Aggregation across joints is explicit: `Slowing` uses the **minimum** per-joint
rate (equivalently the largest absolute error under the monotone rate law); `Stall` and
`Abort` fire if **any** joint triggers; `Complete` requires **all** joints inside
`eps_1`; counters are per joint. `Stall` requires a growing error,
`|v| ≤ stall_velocity`, and a saturated command for `stall_cycles`; the kinematic half is
the provable lemma

```lean
theorem stall_error_grows
  (q_meas q_ref : ℝ → ℝ) (t0 v_min : ℝ)
  (hclamp : ∀ t ≥ t0, q_meas t = q_meas t0)
  (href : ∀ t ≥ t0, q_ref t ≥ q_ref t0 + v_min * (t − t0))
  (hv : 0 < v_min) :
  ∀ t ≥ t0, q_ref t − q_meas t ≥ (q_ref t0 − q_meas t0) + v_min * (t − t0)
```

with the corollary that `eps_abort` is crossed in finite time. Full stall soundness,
including the saturation conjunct, is a simulation property in M4, not a theorem.

`Replan` is a one-shot request. With M2 available, the controller calls
`plan_general(measured, target)` and replaces the profile. For a multi-joint move from a
moving state the coordinator first issues a synchronised controlled stop and then a MoveJ,
because independent general profiles have no common time base. The M4 harness may also
report `Replan` and let the caller perform it, which keeps the cycle deterministic.

The M4 plant and harness are fixed-capacity and allocation-free:

```rust
pub struct JointPlant { /* state, optional position clamp */ }
impl JointPlant {
    pub fn step(&mut self, commanded_accel: f64, cycle: f64) -> PlantStep;
}

pub fn run<const N: usize>(
    profile: &JointProfile<N, f64>,
    plants: &mut [JointPlant; N],
    tracker: &Tracker,
    supervisor: &mut Supervisor<N>,
    config: CycleConfig,
) -> RunReport<N>;
```

Cycle order (documented and tested): evaluate the reference at `s`; compute each command;
step the supervisor (rate, errors, counters); step each plant with the command; record the
outcome. The plant is semi-implicit Euler with an optional position clamp that sets
velocity to zero and reports `clamped`; this models an obstacle for the stall test. The
harness records min/max position, max error, max velocity and the cycle at which each
outcome fired.

**Re-plan contract.** `run` stops at the first `Decision::Replan` and returns the report
with the plant and supervisor state intact; it does not attempt to replace the profile
itself. The caller then:

1. builds the replacement — `plan_general(measured, target)` for a single joint, or
   `synchronizedStop` followed by MoveJ-scalar for a multi-joint move;
2. calls `Supervisor::reset(reference_time)` (add this to the API) and swaps the profile;
3. resumes `run`.

If the replacement returns `Err(PlanError::Infeasible)`, the controller holds the current
position and reports `Abort` (or `Holding` until an operator clears it); it never stays on
a stale profile. `CycleConfig` carries `{ cycle, max_cycles }`; `RunReport` carries
`{ cycles, outcome, stall_cycle, replan_cycle, max_abs_position_error, position_min,
position_max, max_abs_velocity }`. A planner callback
`Fn(&[State<f64>; N], &[State<f64>; N]) -> Result<JointProfile<N, f64>, PlanError>` is an
acceptable alternative to the manual loop, provided the `Err` behavior above is preserved.
`Decision::Slowing` carries no payload; the rate is `SupervisorStep.rate`.

**T8 is out of scope.** `Limits` has no position field, and a pointwise tracking-error
bound does not imply a pointwise velocity bound. If position monitoring is wanted, add a
separate `PositionLimits { lo, hi }` and state the honest envelope: a reference inside
`[lo + e_max, hi − e_max]` with tracking error at most `e_max` keeps the measured position
inside `[lo, hi]`; otherwise the supervisor aborts on a measurement outside the band.
`Feasible` also does not by itself imply the reference stays between its endpoints; for
rest-to-rest profiles the separate no-overshoot theorem supplies that.

### 5.5 `no_std`, capacity, error handling

- Fixed arrays, no heap; `MAX_PHASES = 15` is backed by `planGeneral_length_le` and
  `planRest*_length_le`; either rest-to-rest planner uses 7 slots.
- `libm` supplies `sqrt`/`cbrt` under `no_std`; `std` uses the platform methods, following
  `robot-kinematics`' feature pattern.
- NaN/∞ inputs are rejected at `Limits::new` and by the planner's state validation. A
  `Profile` can only contain finite values by construction; `eval` is total on finite
  inputs.
- No panics on the control path. Capacity errors are returned, not asserted; tests
  exercise the maximal 15-segment general case.

### 5.6 App integration (implemented)

The app's Motion tab (issue #13) implements the first command type, `movej`, on top of
`robot-motion`. It is a **kinematic replay**, not the M4 plant/supervisor harness:

- `MotionRuntime` (`crates/robot-app/src/motion.rs`) holds the queue, the draft command,
  the displayed `PlaybackPlan` and the playback clock. `motion::advance_motion` runs in
  `Update` before `scene::sync_joints`, evaluates the plan at the current time and writes
  `RobotState::runtime_angles_deg`; the 3D view and the Parameters-tab joint fields follow.
  The frame delta is capped at 0.1 s so a stall cannot teleport the arm.
- The app boundary is degrees. Command start/stop and the command's V/A/J are in degrees
  and seconds; the planner is unit-agnostic, so no conversion is needed. Runtime angles
  stay continuous and unwrapped: nothing in the motion path calls `wrap_angle` or
  `nearest_representative`, and a 359° → 361° move is a 2° move.
- `movej` is the scalar joint-space-line mode, timed with
  `plan_movej_scalar_optimal`. All joints follow `q_i(t) = q0_i + s(t) Δq_i` and finish
  together; the slowest joint sets the pace. `plan_movej_scalar` (the conservative verified
  default) remains in the crate and the exact tests.
- Every command carries one V/A/J request. `robot_parameters.json` carries a
  `motion_limits` array with one physical V/A/J row per joint. The effective limit is the
  component-wise minimum: a command below the physical limits runs exactly as written, and
  one above them is capped, with the cap shown in the Motion tab. Position limits are not
  modeled.
- The queue is the user's authored list. The playback plan inserts transition MoveJs from
  the current pose whenever a command's start differs from the pose the arm is in — the
  first command, or a gap after an edit or import. Transitions are **not** written back
  into the queue, so replaying from a different pose does not accumulate synthetic
  commands. Commands are rest-to-rest; the arm reaches zero velocity at each junction.
- Command JSON is one `{"type":"movej", ...}` object; queue JSON is
  `{"schema":"robot-app.motion-queue","version":1,"commands":[...]}`. Both are
  copy-pasteable, and the importers are atomic: a queue that fails validation or planning
  leaves the old one in place.
- The Motion tab keeps the 3D view in the central rect and puts the command editor and
  queue on the left, with joint-angle, tool-XYZ and unwrapped-RPY graphs in a bottom
  panel. The graphs show the whole plan and a cursor at the playback time.

**Planned command types.** The other three are specified here but not implemented. They
need a sampled-trajectory segment beside the analytic `JointProfile`s:

- `lin`: interpolate the tool pose linearly in position and with a rotation interpolation
  (slerp or axis-angle) in Cartesian space, sample at a fixed rate, and solve each sample
  with the existing closed-form IK. Reject a path with an unreachable sample or a branch
  discontinuity. Joint limits are checked on the sampled joint trajectory.
- `circle`/`ellipse`: a center, plane normal, two radii, start/end angle and direction
  define the arc; sample the Cartesian path and solve it the same way. An ellipse segment
  needs a parameterization decision (arc-length vs. angle) before the schema is fixed.
- `waypoints`: a pose list plus blend radii; replace each corner with a circular or
  polynomial blend, then sample and solve. This is the type that removes the rest-to-rest
  junctions the current `movej` queue necessarily has.

## 6. Golden data and verification

### 6.1 Generator

`lean/MotionTestData.lean` is a generator in the pattern of `KinematicsTestData.lean`:

- It restates `State`, `Segment`, `Profile` and cubic evaluation over `ℚ`.
- It constructs cases from **rational shapes**, not from arbitrary endpoints:
  choose `A`, `J`, `V`, `q0` and rational durations/peaks; derive `q1` and the segment
  list. This makes every emitted duration, jerk, position and sample state exact.
- It emits `phase_starts` as well as the segments, so a consumer can check the fold at
  every boundary without re-deriving it.
- It keeps every numeral below `2^53` in magnitude where the case allows, so
  `Ratio::to_f64` is a single correctly-rounded division; the corpus-integrity test
  asserts the bound.
- It re-checks every case by evaluation before writing: endpoint reached, rest boundary,
  every phase-start/advance identity, per-segment endpoint bounds, acceleration sign
  constant within each segment, jerk bound, and the case-defining equation
  (`2Jt_r³ = D`, `v_p²/A + v_p t_j = D`, or `A(t_j+t_a) = V`).
- It refuses to write if any check fails, matching the existing generators.
- It writes `test_data/motion_profiles.json`; `cargo xtask gen-golden` runs it,
  `check-golden` fails on drift.

The corpus has three modes. **Conservative** cases are generated from the rational
template of §3.8 and are exact for both the planner and the evaluator.
**Optimal** cases are generated from the rational shapes of §6.2; the expected data is
exact, while the f64 optimal planner is compared with tolerance. **General** cases cover
the stop–move–start planner and its reject predicate; the expected data is still exact
(rational brake durations are chosen in §6.2), but the f64 general planner is compared
with tolerance because its brake profile uses `sqrt`.

The generator never calls `Real.sqrt`/`cbrt`. It chooses perfect squares/cubes so the
planner's roots are rational witnesses, then checks the defining equation exactly:

- **Conservative:** choose rational `A,J,V`; `τ = min 1 (min (A/J) (V/J))` is rational.
  If `D ≥ Δmin = 2Jτ³`, use `j = J` and `τ_c = (D − Δmin)/(Jτ²)`; otherwise use
  `j = D/(2τ³)` and `τ_c = 0`. `D = 0` returns the empty profile before any division.
  Every duration and state is rational.
- **Cruise, A reached:** choose `A,J,t_a,t_c` with `t_j=A/J`, `V=A(t_j+t_a)`, `V>v_A`;
  `D = D(V) + V t_c`.
- **Cruise, triangular:** choose `J=q²`, `t_r,t_c`; `V=J t_r² < v_A`;
  `D = 2V t_r + V t_c`.
- **Peak-no-cruise (Case B):** choose `A,J,t_a`; `v_p=A(t_j+t_a)`, `v_p>v_A`;
  `D = v_p²/A + v_p A/J`; require `D < D(V)`.
- **Triangular (Case C):** choose `J=q²`, `t_r`; `v_p=J t_r²`;
  `D = 2J t_r³ = 2v_p t_r`; require `D < D(V)` and `v_p < v_A`.
- **General:** choose `a0`, `v0`, `a1`, `v1` and rational stop/start durations; for a
  triangular brake choose the post-ramp velocity as `J t_r²` so `t_r` is a rational
  witness. Derive the positions by folding the segments; the middle is one of the
  conservative cases above. The expected data is exact; the f64 general planner is
  compared with tolerance.
- **Reject:** choose a state that violates `stop_feasible` exactly.

For `V < v_A`, `D ≥ D(V) = 2V·sqrt(V/J)` is compared as `D²·J ≥ 4V³` (both sides
nonnegative), never by evaluating the root. Because `J=q²` and the chosen durations are
rational, the Case C cbrt input is exactly `(q t_r)³`, and the Case B discriminant is
exactly `(v_A + 2v_p)²`; the f64 planner's `sqrt`/`cbrt` therefore differ from the exact
answer only by rounding, not by a different algebraic value.

Boundary cases use small rational margins (for example `D(V) ± 1/1000`) rather than
exact f64 equality. Exact-equality kind assertions are reserved for cases whose values
are exactly representable integers or small dyadics. The corpus marks such cases
`"threshold": true` and compares the trajectory rather than the segment list.

### 6.2 Exact case construction and exact checks

The generator's checks are exact over `ℚ`, including feasibility at critical points:

- `a(τ)` is linear, so its extrema on a segment are at the endpoints.
- `j` is constant.
- `v(τ)` is quadratic; its extrema are the endpoints or the vertex `τ* = −a0/j` when
  `0 < τ* < dur`.

The generator emits `max_speed`, `max_accel` and `max_jerk` per phase (and per joint for
sync) as rationals and checks them against the limits. This is a **complete** feasibility
check for a rational constant-jerk profile, not a sample. The Rust `Profile<Ratio>` test
can therefore compare the maxima with `==`.

The corpus must cover: all four M1 kinds; every slot pattern (A reached, triangular with
cruise, no-cruise, pure triangular) in the uniform 7-slot form; both displacement signs;
zero motion; `t_a = 0`; `t_c = 0`; `V = v_A`; negative limits rejected; general
accept/reject cases; and sync cases with a stationary joint and an all-stationary move.

Verified representative rest-to-rest cases (`V,A,J = 3,2,4` unless noted; durations in
7-slot order; every number rational):

### 6.4 Rust tests

`crates/robot-motion/tests/golden_motion.rs` (embedding the document with `include_str!`,
as the kinematics suite does):

1. **Exact profile checks.** Build `Profile<Ratio>` from the expected segments
   (`from_parts`), evaluate at every sample with `==`, check every `phase_start`, and check
   `max_speed/max_accel/max_jerk` exactly. This runs the same generic code as production.
2. **Exact stretch/sync checks.** Build the source `Profile<Ratio>`, call `stretch` and
   `synchronize`, and compare the expected phases, total times and samples with `==`.
   Zero-motion joints are constant holds of `sync_time`, not empty profiles: the rest-to-rest
   planners return an empty profile for `D = 0`, while `hold` is a one-segment profile
   `(duration, jerk = 0)`. The sync goldens pin that difference explicitly (including
   `sync_time = 0`, where the hold has a zero-duration segment).
3. **Planner checks.**
   - `plan_rest_conservative::<Ratio>` is exact: call it with the case's rational inputs
     and compare the produced durations, jerks, phase starts and samples with `==`.
   - `plan_rest_to_rest` (optimal) and `plan_general` are f64: compare kind, total time,
     segment count, durations, jerks and `phase_start(i)` with tolerance
     `1e-12 * max(1, |expected|)`; evaluate at every sample and compare. Report the observed
     worst case in the failure message.
4. **Reject cases.** Read `reject_cases` and assert the `PlanError` variant named by
   `expected_error` (`Infeasible`, `NonPositiveLimit`, `NonFiniteInput`). Non-finite values
   are exercised by property tests rather than JSON sentinels.
5. **Corpus integrity.** Assert every kind and all six joints appear, every numeral is a
   string, and every expected numeral is below `2^53` in magnitude where the case allows
   (so `Ratio::to_f64` is a single correctly-rounded division).
6. **Threshold cases.** Compare the trajectory at sample times; a segment-list or kind
   difference is allowed only for cases marked `"threshold": true` and within tolerance.

The exact `Profile<Ratio>` tests are the strong check: they cover generator, schema,
evaluation, stretch and synchronisation with no tolerance. The f64 planner tests cover the
algorithm and case selection with the declared tolerance.

### 6.5 Property and integration tests

`tests/properties.rs`, using the repo's seeded `splitmix64` style (proptest for magnitude
coverage, deterministic grids for boundary sweeps):

- `plan_rest_conservative_is_feasible`: random `q0`, `q1`, limits; dense sample; check
  `|v| ≤ V`, `|a| ≤ A`, `|j| ≤ J`; start/end; monotonicity; no NaN. The same planner runs
  over `Ratio` in the exact golden test.
- `plan_rest_to_rest_is_feasible` (M1-opt): the same properties for the optimal planner,
  with a small relative slack.
- `plan_general_is_feasible`: random states; check `stop_feasible` against a reference
  predicate; accepted cases yield feasible profiles with the right endpoints; rejected
  cases return `Infeasible`.
- `plan_is_deterministic`: two calls are bit-identical.
- `plan_length_bounds`: the conservative and optimal rest-to-rest profiles have at most 7
  segments; the general planner has at most 15; exercise the maximal general case.
- `case_boundaries_are_continuous`: sweep `D` across `D_full(V)` and `2A³/J²` with small
  rational margins; outputs stay feasible and nearby; do not assert the kind at equality.
- `stretch_feasible` / `state_at_stretch`: random `k ≥ 1`; check total time and the state
  relation, including nonzero start states; `stretch` rejects `k < 1`.
- `synchronize_feasible` / `synchronize_total_time`: random rest-to-rest profiles; all
  total times equal `sync_time`; feasibility; a zero-motion joint is a constant hold;
  all-zero and `n = 0` cases.
- `synchronized_stop_ends_together`: from random moving states, each stop+hold profile
  ends at rest and at the common `T_max`; the stopped configuration is then a valid MoveJ
  start.
- `plan_movej_scalar_path` / `plan_movej_scalar_feasible`: the joint path is exactly
  `q0_i + s(t) Δq_i`; every joint respects its limits; a zero-displacement joint is
  skipped in the effective-limit min. `plan_movej_scalar_all_stationary` covers the
  all-zero case (empty scalar move, total time 0).
- `stall_error_grows`: the kinematic lemma under a clamp and a monotone reference.

M3's exactness boundary is worth stating separately. The **joint-space** trajectory and
the synchronization durations are exact over `Ratio`; the TCP endpoint poses can be exact
only when the endpoint angles are supplied as Pythagorean cosine/sine pairs, as in
`kinematics_frames.json`. Interior TCP poses are tolerance-based (a rational angle in
radians has rational cosine/sine only in trivial cases), and MoveJ-sync makes no TCP path
claim; MoveJ-scalar makes the joint-space straight-line claim, not a Cartesian one.

- Negative tests: zero/negative limits, NaN/∞ state, a non-rest profile rejected by
  `RestProfile::new`/`synchronize`, overflowing displacement (`f64::MAX` → typed error, no
  NaN), a phase list longer than `MAX_PHASES`, `stretch` below one, and non-finite
  supervisor inputs.

`tests/supervisor.rs` uses the headless plant:

- a semi-implicit Euler plant with optional position clamp and command saturation;
- time-scaling: a lagging plant slows the reference; the rate stays in `[0, 1]`;
- stall: a clamp makes the error grow while the command saturates; `Decision::Stall`
  within `stall_cycles + 1`;
- re-plan: a disturbed state produces `Replan`; with M2, the new profile starts at the
  measured state and is feasible;
- abort: persistent error beyond `eps_abort` for `abort_cycles`, and non-finite inputs;
- completion: no-obstacle run reaches the target within the declared error band;
- determinism: identical inputs produce identical cycle reports.

### 6.6 Verification boundary

Add to `docs/verification.md`:

- The motion theorems are about `ℝ`. The Rust is `f64`. No floating-point error bound is
  proved.
- The polynomial layer (`Profile<Ratio>` evaluation, stretch, synchronize) and the
  conservative `plan_rest_conservative::<Ratio>` are exact and compared with `==`. The
  optimal planner's `sqrt`/`cbrt` results are compared with a declared tolerance; the
  golden inputs are perfect squares/cubes so the algebraic value is rational.
- `planRestConservative` is the verified M1-default. M1-opt's Cases B/C are a named,
  non-gating proof target; the Rust optimal planner is tested but not proved unless those
  proofs land.
- Derivatives in `FeasibleOn` are quantified on `Ioo`; the state-level `Feasible` uses the
  polynomial velocity/acceleration fields on `Icc`. The boundary conditions are separate
  theorems.
- Symmetric limits, finite states, no position limits, no torque/dynamics.
- `planGeneral`'s `None` is exact for the stop–move–start decomposition (`Viable`), not a
  global infeasibility certificate. A direct profile that never passes through rest can
  exist outside `Viable`; `stopFeasible_necessary` covers only profiles ending at rest.
- M5's derivative bounds are trusted/sampled, not proved; `cartesian_path_feasible` is
  conditional, and the certifier's abort path is the part the tests enforce.
- The app is a kinematic viewer; M4 is a headless harness.
- `sync`/`synchronize` is rest-to-rest only; general re-plan uses stop-then-MoveJ.

## Appendix A — Corrected S-curve formulas

Notation: `A = a_max`, `V = v_max`, `J = j_max`, `t_j = A/J`, `v_A = A²/J`.
For a symmetric acceleration half to peak velocity `v`:

```
d(v) = v · sqrt(v/J)                        0 ≤ v ≤ v_A
     = v · (t_j + v/A) / 2                  v_A ≤ v
```

At `v = v_A`: `d = A³/J²`. `D_full(V) = 2 d(V)`.

Rest-to-rest, `D > 0`. All cases use the same 7-slot jerk pattern
`(+J, 0, −J, 0, −J, 0, +J)`; a slot the case does not use has duration zero:

```
Case A (D ≥ D_full(V)):
  V ≥ v_A:  t_a = V/A − t_j,  t_c = (D − D_full(V))/V
            durations (t_j, t_a, t_j, t_c, t_j, t_a, t_j)
  V < v_A:  t_r = sqrt(V/J),  t_c = (D − 2V t_r)/V
            durations (t_r, 0, t_r, t_c, t_r, 0, t_r)

Case B (D < D_full(V), V ≥ v_A, D ≥ 2A³/J²):
  v_p = (A/2)(sqrt(t_j² + 4D/A) − t_j),  t_a = v_p/A − t_j
  durations (t_j, t_a, t_j, 0, t_j, t_a, t_j)

Case C (otherwise):
  t_r = cbrt(D/(2J))
  durations (t_r, 0, t_r, 0, t_r, 0, t_r)

Case D: D = 0 → empty profile.
```

Displacement identities:

```
Case A (A reached):  d(V) = A t_j² + (3/2)A t_j t_a + (1/2)A t_a² = V(t_j + V/A)/2
Case B:              D = 2 d(v_p) = v_p(t_j + v_p/A)
Case C:              D = 2 J t_r³
```

The draft's `d_acc` correction term and `5/12` triangular coefficient are both wrong; the
identities above are the ones the implementation and the Lean proof use.

## Appendix B — General planner conditions

```
rev(s) = { q := s.q, v := −s.v, a := s.a }

stop_feasible(s, lim) :=
  |s.a| ≤ A ∧ |s.v| ≤ V ∧ |s.v + s.a·|s.a|/(2J)| ≤ V

v1 = s.v + s.a·|s.a|/(2J)
```

`stop_profile`:

```
ramp  = if s.a = 0 then [] else [(dur = |s.a|/J, jerk = −sign(s.a)·J)]
brake = brake_profile(v1, lim)
stop_profile = ramp ++ brake
```

`brake_profile(v)`:

```
v > 0, v ≥ v_A:  [(−J,t_j), (0,t_a), (+J,t_j)],  t_a = v/A − t_j
v > 0, v < v_A:  [(−J,t_r), (+J,t_r)],           t_r = sqrt(v/J)
v < 0:           mirror the positive case
v = 0:           []
```

`plan_general`:

```
Viable(s0, s1, lim) = stop_feasible(s0, lim) ∧ stop_feasible(rev(s1), lim)

if not Viable(s0, s1, lim): return None
stop  = stop_profile(s0, lim)
start = reverse(stop_profile(rev(s1), lim))
mid   = plan_rest_conservative(stop.end.q, start.start.q, lim)
return append(append(stop, mid), start)
```

Segment bound: `4 + 7 + 4 = 15`.

The rejection is exact for this decomposition. `stop_feasible` is necessary for any
jerk-limited profile that ends at rest, by the acceleration-removal argument in §3.5.

## Appendix E — Glossary

- **Profile** — a start state, an end state, and ordered cubic segments of constant jerk.
- **Segment** — one cubic piece, `(duration, jerk)`; a `Profile` also stores each segment's
  entry state.
- **PlanKind** — `ZeroMotion`, `Conservative`, `Cruise`, `PeakNoCruise`, `Triangular`,
  `General`. `Conservative` is the verified M1-default template; the others are M1-opt or
  the general planner.
- **Rest-to-rest** — zero velocity and acceleration at both ends.
- **Feasible** — velocity, acceleration and per-segment jerk inside the limits.
- **Stretch** — affine time reparameterisation `q(t) ↦ q(t/k)`, with start derivatives
  scaled by `1/k` and `1/k²`; `k ≥ 1` preserves feasibility.
- **StretchTo** — stretch a profile to a specified total time `T ≥ T_i`; a zero-duration
  profile becomes a constant hold.
- **Stop–move–start** — general-boundary planner: brake to rest, rest-to-rest move, then
  accelerate to the target state.
- **MoveJ-scalar** — one S-curve `s(t)` with `q_i = q0_i + s Δq_i`; a straight line in
  joint space. **MoveJ-sync** — per-joint profiles stretched to a common duration; not
  generally a joint-space line.
- **comp_bounds** — the chain-rule composition lemma shared by time scaling and Cartesian
  certification.
- **Certificate** — `(M1, M2, M3, V, A, J)` plus the three inequalities that make a
  Cartesian path feasible under conservative timing.
- **TOPP** — time-optimal path parameterisation; out of scope for M1–M4.
